# Текущее состояние

C++17 application core проверяется на ПК через CMake. CubeIDE пока собирает
исходную прошивку: новые модули ещё не включены в его сборку.

- `app/kinematics`: 3–6 вращательных суставов, транзакционная проверка модели,
  IK float32, фиксированные буферы. Геометрия и преобразования базы/инструмента
  задаются полностью при активации. IK: 300 итераций, 16 backtracking trials,
  допуск 20 мкм, damping 0.005, joint scale 1, максимальный шаг 0.2 рад.
  Это начальные параметры, требующие измерений на целевых моделях и МК.
- `app/application`: режимы настройки/runtime, FIFO 8 запросов и 8 результатов.
  Каждый запрос хранит ID, цель и начальное приближение. Повторяющиеся ID пока
  не запрещены: клиент должен обеспечивать уникальность среди активных запросов.
  Результаты читаются без удаления; ACK удаляет только голову с совпадающим ID.
  При полном буфере результатов выполнение приостанавливается, запросы
  принимаются до заполнения входной очереди. Ошибочные расчёты также дают результат.
- При переходе к настройке запросы и результаты удаляются. Текущий интерфейс
  синхронный, одного владельца: нельзя вызывать методы из разных задач/ISR.
  Для асинхронной отмены выполняющегося IK потребуется адаптер с номером сеанса,
  который отбросит устаревший результат; сам решатель сейчас не прерывается.
- Нет heap в application core, исключений и RTTI в его сборке.

## Проверка

Из каталога проекта CubeIDE:

```
cmake -S . -B /tmp/manipulator-core-host
cmake --build /tmp/manipulator-core-host
ctest --test-dir /tmp/manipulator-core-host --output-on-failure
```

По умолчанию используется сабмодуль `third-party/manipulator_kinematics`.
Путь можно задать через `-DKINEMATICS_PATH=/absolute/path`.

## Следующие этапы

1. Карта регистров и обработчики nanoMODBUS: staging-конфигурация, маска
   заполненных полей, явные APPLY/SUBMIT/ACK и документированные исключения.
2. RTOS-адаптер: отдельные задачи протокола и расчётов, владение моделью,
   отмена через номер сеанса, очереди rtos_layer.
3. Подключение к C++17 сборке CubeIDE.
4. UART/RTU: приём, тайминги кадров, ошибки и интеграционные тесты по USB–UART.
5. Flash: формат с версией/CRC, резервирование секторов, сохранение командой SAVE.

UART, Flash и Modbus пока не реализованы. Пустые каталоги предназначены
для этих следующих этапов; они не означают готовые драйверы.

## Реализованный протокол и RTOS-адаптер

См. `modbus.md`. `application/engine.hpp` — mailbox с одним worker и номером
сеанса. `platform/freertos/service.hpp` сериализует обмен через статический
mutex rtos_layer; вызов IK выполняется вне mutex. Уведомления index 0 будят
worker при поступлении команды/ACK. Конфигурация и запросы — снимки без heap.
`Controller` остаётся ранним синхронным вариантом для исходных unit-тестов;
для интеграции используйте Engine/RtosService, а не два контроллера одновременно.

Создавайте RtosService со статическим временем жизни. Создайте worker через
xTaskCreateStatic, передав RtosService::worker_entry и адрес сервиса. Вызовите
bind_worker(handle) до старта scheduler и до любых команд. Создайте Registers
и Server в protocol task/статическом storage. Не используйте API сервиса из ISR.
UART task и worker ещё не добавлены в CubeIDE; размеры стеков измерим на МК.

Linux integration:

```
cmake -S . -B /tmp/manipulator-core-host \
  -DAPPLICATION_FREERTOS_PATH=/absolute/path/to/FreeRTOS-Kernel
cmake --build /tmp/manipulator-core-host
ctest --test-dir /tmp/manipulator-core-host --output-on-failure
```

Проверяются протокол на уровне регистров, отмена старых результатов/конфигурации,
обратное давление очередей и реальный обмен protocol/IK задач на POSIX FreeRTOS.
Адаптер Server собран с nanoMODBUS; RTU integration проверяет кадры в памяти, CRC,
FC04/06 и Modbus exceptions. Физический UART пока не подключён.
