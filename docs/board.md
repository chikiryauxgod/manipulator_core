# Прошивка STM32F401CCU6

## Подключение

USB–UART должен работать с логическими уровнями **3.3 В**.

| Black Pill | USB–UART |
|---|---|
| PA2 (USART2 TX) | RX |
| PA3 (USART2 RX) | TX |
| GND | GND |

Питание платы — отдельно через USB. Не соединяйте выходы питания двух источников.
По умолчанию: **115200, 8E1, slave 1**. При отключении parity используется 8N2.
Скорости 38400–115200; тайминги RTU t1.5=750 мкс и t3.5=1750 мкс.
TIM1 — HAL tick, TIM2 — RTU timer, SysTick — FreeRTOS.
PA13/PA14 и NRST остаются для ST-Link. UART не использует HAL UART и DMA:
приём по IRQ, очередь на четыре полных ADU, передача с ожиданием TXE/TC.

## Сборка и запуск

1. `git submodule update --init --recursive`.
2. После обновления кинематики выполнить `python3 tools/generate_kinematics_config.py`.
3. Импортировать существующий проект в CubeIDE, Refresh, Clean, Build.
4. Прошить Debug/manipulator_core.elf через SWD и запустить.

Сборка firmware проверяется ARM-компилятором CubeIDE на пользовательской машине.
В текущей среде доступны только host-тесты и синтаксическая проверка аппаратных файлов.
Не изменяйте .ioc с последующей генерацией вслепую: UART/TIM2 и запуск native
FreeRTOS добавлены вручную. CubeMX может заново создать SVC/PendSV/SysTick handlers;
ими должен владеть только ARM_CM4F port, без дублирующих функций в stm32f4xx_it.c.

## Проверка с ПК

В отдельном Python venv установите `pyserial`, затем:

```
python tools/modbus_client.py --port /dev/ttyUSB0 status
python tools/modbus_client.py --port /dev/ttyUSB0 init tools/model_3r.json
python tools/modbus_client.py --port /dev/ttyUSB0 ik 0.3 0 0.3 --initial 0.1 0.2 0.3
python tools/modbus_client.py --port /dev/ttyUSB0 save
```

IK-клиент читает и подтверждает результат. SAVE разрешён только при пустой очереди,
без расчёта и непрочитанных результатов. Timeout клиента 5 секунд учитывает стирание
Flash; не отправляйте новые запросы, пока SAVE не завершится. Автоматических повторов
команд нет: при потере ответа сначала проверяйте состояние/ID, чтобы не дублировать работу.

После перезапуска сохранённая модель загружается в staging, но runtime не включается:

```
python tools/modbus_client.py --port /dev/ttyUSB0 apply
python tools/modbus_client.py --port /dev/ttyUSB0 status
```

Без валидной записи используются стандартные UART/slave, модель нужно передать заново.
LOAD загружает staging вручную только в режиме настройки. Полная карта — modbus.md.

## Flash и память

Linker разрешает прошивке только первые 64 КБ Flash (секторы 0–3).
Секторы 4 (64 КБ) и 5 (128 КБ) содержат две чередуемые копии конфигурации.
Каждая запись содержит версию, счётчик, модель, UART/slave, параметры IK, CRC32
и финальный commit marker. До завершения записи прежняя копия не стирается.
Изменение политики IK в прошивке инвалидирует несовместимую сохранённую запись.
Полное стирание Flash через программатор удаляет настройки; обычная загрузка ELF
не должна стирать зарезервированные секторы. Это следует проверить в выбранном программаторе.

Стирание внутренней Flash приостанавливает исполнение кода/обработку IRQ на этом МК.
Во время SAVE возможна потеря UART-данных и пауза счётчиков FreeRTOS/HAL.
Таймауты и временные измерения после такой операции нельзя использовать как wall clock.

## Диагностика и аппаратная приёмка

`firmware_diagnostics`: heartbeat, HAL/RTOS ticks, минимальный остаток стеков
(в 32-битных словах), ошибки Modbus, отброшенные кадры, загрузка настроек, assert.
Проверить на новой плате:

- запуск и обмен в 8E1/8N2, сохранение UART-настроек с применением после reset;
- FK-проверку результатов IK, предел времени и остаток стеков под нагрузкой;
- восстановление связи после CRC/ошибок UART/переполнения очереди;
- повторную настройку во время IK и отсутствие результата предыдущего сеанса;
- SAVE/LOAD, перезапуск и обрыв питания в разных фазах записи;
- тайминги t1.5/t3.5 на границах с логическим анализатором.

На ПК проверяются формат/CRC и логика, а не реальные Flash, IRQ или электрика.
Watchdog и web-интерфейс в эту прошивку пока не входят.
